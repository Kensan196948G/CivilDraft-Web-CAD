2. 認証局（CA）発行証明書チェーンの組み込み

2-1. 署名用証明書の準備

ブラウザ側で扱うため、秘密鍵は PKCS#8 PEM（RSA 2048/3072）を用意します。openssl で CSR を作成し、CA へ申請します。

# 1) 秘密鍵と CSR の作成（社内 CA / 商用 CA 共通）
openssl req -new -newkey rsa:3072 -nodes -sha256 \
  -keyout signer.key -out signer.csr \
  -subj "/C=JP/O=＜組織名＞/OU=＜部署名＞/CN=＜署名者名＞"

# 2) SAN が必要な場合は設定ファイルで追加
#    [ req ] distinguished_name = dn
#    [ san ] subjectAltName = email:signer@example.co.jp

# 3) 申請内容の確認
openssl req -in signer.csr -noout -text
⚠ 電子署名法上の「本人確認済み電子署名」を求める場合、商用認証局のドキュメント署名証明書（例: 各社「電子署名用証明書」）を利用してください。社内 CA の場合は運用規程（秘密鍵管理・失効）を整備してください。

2-2. チェーン（証明書バンドル）の準備

CA から発行された「署名者証明書」と「中間 CA 証明書」を PEM で受け取り、連結します。

# signer.pem + 中間 CA を連結（順序: 署名者 → 中間 → ルートは省略可）
cat signer-cert.pem intermediate-ca.pem > chain.pem

# チェーン検証（ルート CA がある場合）
openssl verify -CAfile root-ca.pem -untrusted intermediate-ca.pem signer-cert.pem

2-3. コード拡張（複数証明書の埋め込み）

現状の buildSignedData(signerInfo, certificates) は単一証明書を想定しています。チェーン全体（署名者＋中間）を配列で渡せるよう拡張します。

// src/domain/pdf/pdfSignaturePades.ts の拡張イメージ
// 1) 入力に chain を追加
//    signPdfEmbedded({ ..., certificateChain?: Uint8Array[] })
//
// 2) buildSignedData は [0] IMPLICIT CertificateSet として
//    証明書 SEQUENCE を連結したまま埋め込む（現在の実装のまま配列で渡す）
//    → certificates: certificateChain ?? [certificate.certificateDer]
//
// 3) SignerIdentifier は「署名者証明書」の issuerAndSerialNumber を使用
//    （自己署名時の空 Name をやめ、チェーン先頭の証明書から取得）
⚠ 埋め込み領域のサイズ見直しも必要です。チェーン＋TSA トークンで 2〜4 KB 増えるため、SIGNATURE_RESERVED_HEX_LEN（現在 8192 = 4096 バイト）を 16384（8192 バイト）以上へ拡大してください。

2-4. 実装後の自己検証（openssl）

# Detached（.p7s）の検証: PDF 本体と署名を分離して検証
openssl cms -verify -inform DER -in signature.p7s \
  -content document.pdf -CAfile chain.pem -purpose any

# 埋め込み署名の検証は「ByteRange の範囲」を切り出して同様に検証する
# （抽出方法は 4 章の検証手順を参照）

3. タイムスタンプ局（RFC 3161）の連携

3-1. TSA の選択

種類例備考
商用 TSADigiCert / GlobalSign / SECOM 等のタイムスタンプサービス法的証明力・監査に強い。契約・課金あり
公開テスト TSAFreeTSA（freetsa.org）動作確認用。本番利用は不可
社内 TSAADCS タイムスタンプサービス等運用規程が要件を満たす場合
⚠ 本番利用には、発注者・監査要件に合う TSA（RFC 3161 対応・時刻の信頼性・長期検証可能なトークン）を選定してください。

3-2. openssl で TSA の動作確認

# 1) タイムスタンプ要求（TSQ）の作成
openssl ts -query -data signature.bin -sha256 -cert -out request.tsq

# 2) TSA へ送信（例: FreeTSA。本番は選定した TSA の URL を使用）
curl -sS -H 'Content-Type: application/timestamp-query' \
  --data-binary @request.tsq -o response.tsr \
  https://freetsa.org/tsr

# 3) 応答（TSR）の確認
openssl ts -reply -in response.tsr -text | head -40

# 4) TSA 証明書で検証
openssl ts -verify -data signature.bin -in response.tsr -CAfile tsa-ca.pem

3-3. コード拡張（signature-time-stamp 属性）

PAdES では SignerInfo の unsignedAttrs に id-aa-signatureTimeStampToken（OID 1.2.840.113549.1.9.16.2.14）を追加します。

// 追加する属性の構造（RFC 3161 / ETSI EN 319 122）
// unsignedAttrs [1] IMPLICIT SET OF Attribute
//   Attribute {
//     attrType  = id-aa-signatureTimeStampToken
//     attrValues = [ TimeStampToken (CMS SignedData of TSR) ]
//   }
//
// 実装手順:
// 1) CMS 署名の DER（signerInfo の signature 値）を入力として
//    openssl ts -query 相当の TSQ を生成（または外部ライブラリを使用）
// 2) TSA へ送信して TSR（TimeStampToken）を取得
// 3) unsignedAttrs を DER エンコードして signerInfo 末尾へ追加
// 4) 予約領域を拡大（2-3 と同様）
//
// 検証順序（重要）:
//   署名検証 → 署名値のダイジェストが TSR の messageImprint と一致
//   → TSA 証明書の信頼チェーンと有効期間を検証
⚠ TSA 連携は非同期通信になるため、Worker の実行時間制限（CPU 時間）やタイムアウトに注意し、署名生成はブラウザ側（クライアント）で行う現行設計を維持してください。

4. 最終検証手順

  1. 構造検証: 埋め込み PDF を pdf-lib / 他ビューアで開き、署名フィールド（署名パネル）が表示されることを確認。
  2. チェーン検証: Adobe Acrobat の「信頼済み証明書」へルート CA を登録し、「署名者の検証」が成功すること（自己署名版では「署名者の信頼が未設定」表示になるので、CA 版で成功すること）を確認。
  3. ダイジェスト検証: ByteRange の範囲ダイジェストと CMS の messageDigest 属性が一致すること（既存のユニットテストで担保済みの手法を再実行）。
  4. TSA 検証: openssl ts -verify で TSR が有効（メッセージインプリント一致・TSA 証明書有効）であること。
  5. 回帰: npm test（PAdES 関連テスト含む）・lint・typecheck・build が全 PASS すること。
