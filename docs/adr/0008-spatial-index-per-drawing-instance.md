# ADR-0008: 空間索引（R-tree）はグローバルシングルトンではなく描画インスタンス単位で保持する

## Status

Proposed（Phase 0棚卸し由来、2026-07-15）

## Context

Civil-Drawの`spatialIndex.ts`（rbushラッパー）はグローバルシングルトンとして実装されており、単一図面編集を前提とした構造になっている。性能面ではrbushラッパーにより約700倍の高速化（線形探索比）を達成しており、これ自体は高く評価できる（[リスク台帳](../design/phase0/risk-ledger.md)「Phase 0で新たに確認された固有の技術的発見」）。しかし、CivilDraftが複数図面（案件・工区・測点単位の図面群）を同一セッションで扱う可能性がある場合、グローバルシングルトンは図面間でインデックスが混線する構造的リスクを持つ。同様のシングルトンパターンは`layerStore`/`canvasStore`/`toolStore`にも見られる（cross_cutting_risks）。複数図面同時編集要件の有無は、詳細設計仕様書時点でも未確定（open_questions）。

## Decision

空間索引（および関連するlayerStore等の状態）は、描画（Drawing）インスタンス単位でスコープを持つ設計に変更する。rbushライブラリ自体・その高速化アルゴリズムはas_isで継続利用し、シングルトン化のみを解消する（modify）。複数図面同時編集要件が確定した時点で、インスタンス粒度（タブ単位、ウィンドウ単位等）を確定する。

## Consequences

- 性能上の優位性（rbush 700倍高速化）を維持したまま、図面間の状態混線リスクを解消できる
- `layerStore`/`canvasStore`/`toolStore`のシングルトン解消も同一の設計方針の下で足並みを揃える必要がある（cross_cutting_risks項目5）
- 複数図面同時編集要件が最終的に「不要」と確定した場合でも、インスタンス化自体はテスト容易性（テスト間の状態リーク防止）の観点で維持する価値がある
