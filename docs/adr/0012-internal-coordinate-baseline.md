# ADR-0012: 内部座標基準（長さ単位・軸・角度正方向・許容差）を確定する

## Status

Accepted（Phase 1、2026-07-15）

## Context

詳細設計仕様書§4.1は座標・寸法値を単位タグ付き値型（`LengthValue`等）で扱うと定めているが、
基準単位そのものは「Phase 1詳細レビューで確定する」として未確定のまま残されていた。
§36「詳細設計上の未決事項」表のDD-TBD-002は、内部長さ基準単位・軸・角度正方向・許容差の
4項目を「Phase 1座標ADR」を決定条件として明記している。ADR-0005（座標・寸法値は単位タグ付き
値型で扱う）は型システムレベルの決定のみで、具体的な基準単位数値は含んでいない。

Issue #5（幾何演算エンジン群27モジュールの移植）はこれら4項目を内部表現の前提とするため、
着手前に確定しない場合、値型の内部表現が後から変わった際に27モジュール全体で手戻りが
発生するリスクが高い。

本ADRの決定にあたり、継承元資産（Civil-Draw）の既存実装を実地調査した。

- **角度単位の不整合が既に実害として存在する**: `src/utils/shapeTransform.ts`は
  `rotation`フィールド（Konvaの`rotation` propに直接渡す度数法）と、円弧の`startAngle`/
  `endAngle`フィールド（ラジアン）を混在させており、両者の変換に
  `(s.startAngle * 180) / Math.PI`という個別コードが複数箇所に散在している。これは
  Phase 0リスク台帳R-004（`dxfExporter.ts`の`setUnits('Meters')`宣言とmm座標の不整合）と
  同種の「単位不整合の実害」パターンであり、角度正方向を型レベルで固定する必要性を裏付ける。
- **座標軸はCanvas既定系をそのまま踏襲している**: `src/components/Canvas/CanvasArea.tsx`の
  `<Stage scaleX={zoom} scaleY={zoom}>`はX/Y双方に同符号のスケールを与えており、Y軸の
  明示的反転を行っていない。Konva/HTML Canvasの既定座標系（Y軸下向き）がそのまま画面表示の
  基準になっている。
- **許容差は2種類の値が意味を分けずに混在している**: `chamferEngine.ts`、
  `dimensionEngine.ts`、`dxfExporter.ts`、`filletEngine.ts`、`dxfImporter.ts`、
  `rulerUtils.ts`で`1e-9`（ゼロ長判定等の極小距離）と`1e-6`（一般的な距離比較）が
  ファイルをまたいで使われているが、どちらを長さ用・角度用として使うかの明文化された
  基準はない。

## Decision

CivilDraftの内部座標基準を以下のとおり確定する。

1. **内部長さ基準単位: mm**
   継承元資産（Civil-Draw）が実質mm前提で作られており、既存の幾何演算ロジックを
   変換なしで移植できる。IEEE754倍精度浮動小数点数は約15〜17桁の10進精度を持ち、
   日本の平面直角座標系（原点からの距離は最大でも数百km程度 = 10^8〜10^9mm）を
   mm単位で表現しても小数点以下は十分な精度（サブナノメートルオーダー）を維持できるため、
   将来の広域測量座標（Phase 2）を見据えても不足しない。
2. **座標軸: X軸右方向・Y軸下方向**（Canvas/画面座標系）
   既存実装がKonva/Canvas既定座標系を明示的な反転なしに使っていることに合わせ、
   変換コストのない画面座標系を内部基準として採用する。
3. **角度正方向: 内部表現はradian、X軸正方向を0、反時計回りを正**
   既存実装の`rotation`(deg)/`startAngle`・`endAngle`(rad)不整合という実害を踏まえ、
   内部表現をradianに一本化する。度数法はAPI境界（UI表示、DXF入出力）でのみ扱い、
   `domain/units`の変換関数を介する。
4. **許容差: 距離比較 1e-6 mm、角度比較 1e-9 rad**
   既存実装の`1e-9`/`1e-6`混在パターンを、値の性質（長さ用・角度用）で意味づけを
   整理し直したものとして採用する。
5. `src/shared/types/units.ts`に`AngleValue`インターフェースを追加する。
   `AngleUnit`型（`'deg' | 'rad' | 'gon'`）は既に定義済みだが、対応する値型が
   欠落しており、`LengthValue`/`AreaValue`/`VolumeValue`との一貫性を欠いていた。
6. `src/domain/units/`に、内部基準単位とAPI境界単位（cm/m、deg/gon等）間の
   変換関数を実装する。

## Consequences

- Issue #5（幾何演算エンジン群の移植）着手時、27モジュールの内部表現（単位・軸・
  角度・許容差）が確定済みの前提として使えるようになり、手戻りリスクが下がる。
- 既存Civil-Draw実装で確認された角度単位不整合（`rotation`(deg) vs
  `startAngle`/`endAngle`(rad)）と同種の問題を、型システム（`AngleValue`は常に
  単位を明示）と`domain/units`の変換関数への集約で予防できる。
- 内部座標系（X右・Y下・反時計回りを正）は、測量座標系（多くの場合、北を基準に
  時計回りで方位角を測る）とは異なる。Phase 2（土木座標・測量・線形）実装時に、
  画面座標系と測量座標系との変換層を別途設計する必要がある。これは本ADRのスコープ
  外とし、Phase 2着手時に新規ADRで扱う。
- 許容差の使い分け（距離1e-6mm・角度1e-9rad）は、今回整理した意味づけであり、
  実際の幾何演算移植（Issue #5）で数値的に不適切と判明した場合は、本ADRを
  Supersedeする形で改訂する。
